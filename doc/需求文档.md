## 1. 项目定位与总体目标

`vllmpt` 是面向企业知识密集型场景的 AI Agent 后端平台，同时承载通用审批平台业务模块。

核心能力：

- 多模态对话：文本 + 图片 + 文档混合输入；
- RAG 检索增强：文本知识库上传、分块、向量化、语义召回与重排序；
- ReAct 工具调用：模型自主决策调用业务工具；
- 多轮会话记忆：Redis 持久化 + 窗口记忆；
- SSE 流式输出；
- 多模型动态切换；
- 并发治理：单用户并发限制 + 会话级互斥；
- 通用审批平台：模板驱动流程、条件跳过、多级审批、抄送、AI 填表与 AI 决策扩展点。

总体设计原则：

1. **AI 只做增强**：AI 不可用、低置信度、高风险时必须降级为人工，不能成为唯一决策源；
2. **模板驱动**：审批流程、审批人、条件、抄送全部配置化，新增业务不改引擎；
3. **引擎与业务解耦**：`approval/core` 不依赖任何具体业务模块，业务通过 SPI 接入；
4. **失败优先可用**：Redis / MQ 等基础设施故障时，主链路允许降级（如单号随机、幂等放行），由数据库唯一键兜底；
5. **全链路可审计**：节点流转、任务操作、AI 决策、抄送均留痕。

## 3. 通用 AI 能力场景

### 3.1 S1 单用户并发推理限制（已实现）

**业务背景**：大模型推理极度消耗 GPU，必须限制单用户同时进行的推理任务数，避免恶意或异常客户端打满显存。

**需求**

1. 单用户同时最多 N 个推理任务（默认 `limit=3`）；
2. 任务结束立即释放额度；
3. 超额请求返回 `429`，提示「您的并发请求过多，请稍后重试」；
4. 跨实例生效（Redis 共享状态）。

**方案**

- 数据结构：`ai:concurrent:{userId}` ZSet，member = `requestId`，score = 时间戳；
- Lua 原子完成「清理僵尸 member → 计数 → 判断 → 入队」；
- `window-seconds=300` 清理超窗 member，`key-ttl-seconds=600` 兜底过期；
- 接入点：`ChatPiplineController` 的 `/fack` 与 `/stream`，`finally` 中释放。

**验收**

- 连续发起第 4 个同用户请求返回 429；
- 推理结束后 `ZCARD` 归零；
- 慢请求不会被窗口误清理（窗口需大于最慢一次推理耗时）。

### 3.2 S2 同会话推理互斥（已实现）

**业务背景**：同一 `sessionId` 下快速连点两次发送，会导致两个 SSE 流并发修改 Redis 记忆，造成上下文错乱。

**需求**

1. 同一会话同一时间只允许一个推理任务；
2. 第二个请求立即失败，不排队；
3. 锁必须自动续期，避免长推理期间锁过期；
4. 锁必须由持有线程释放。

**方案**

- `ai:session:lock:{sessionId}` Redisson `RLock`；
- `tryLock(0, -1, SECONDS)` 立即返回并启用看门狗续期；
- `/fack` 返回 `409`，`/stream` 推 `[ERROR]` 帧；
- `sessionId` 为空时放行。

**注意**：`RLock` 按 `clientUuid:threadId` 绑定持有者，解锁必须在工作线程的 `finally` 中执行，禁止在 Netty/Reactor 回调线程解锁。

### 3.3 S3 主动取消与推理任务秒级回收（设计完成，未开工）

#### 3.3.1 目标与非目标

目标：

1. 用户点「停止生成」时，秒级中断 LLM 推理流并回收资源；
2. 前端异常断连时，不中断推理，转静默模式生成完再回收；
3. 级联回收：本地注册表清理 + S1 并发额度（ZREM）+ S2 会话锁（unlock）；
4. 跨节点：`USER_STOP` 广播到所有实例，只有持有该 `requestId` 的实例执行。

非目标：

- 不做取消后的业务补偿（半截回答处理见待决策）；
- 不做任务优先级/排队调度；
- 不做「重连后取回静默完成的回答」；
- 不改造 `/fack` 同步接口的取消能力（但复用同一注册表）。

#### 3.3.2 三层防护关系

```
请求进来
  ├─ S1 并发额度 ZSet       防超发 → 保护 GPU 总量
  ├─ S2 会话锁 RLock        防冲突 → 保护单会话上下文一致性
  └─ S3 取消/静默 Pub/Sub   防浪费 → 保护资源回收时效
```

S1/S2 是「入口管控」，S3 是「出口处置」；S3 **不自己释放资源，只打标记**。

#### 3.3.3 数据结构

Redis：

| 名称 | 类型 | 说明 |
|---|---|---|
| `ai:cancel:broadcast` | Pub/Sub channel | `USER_STOP` 广播，所有实例订阅 |
| `ai:cancel:flag:{requestId}` | String | 可选取消标记，`SET NX EX 60`，兜底广播丢消息 |

广播 payload 使用 JSON 字符串（不是 POJO），避免跨版本序列化耦合：

```json
{
  "requestId": "8f14e45f-ea0e-4c1a-9d0b-2c5f6a7b8c9d",
  "userId": "s1",
  "sessionId": "s1",
  "intent": "USER_STOP",
  "ts": 1758500000000
}
```

`intent` 取值：

| 值 | 是否广播 | 说明 |
|---|---|---|
| `USER_STOP` | ✅ | 用户主动停止，硬中断 |
| `CLIENT_DISCONNECT` | ❌ 本地直调 | 前端断连，软中断（静默） |
| `SILENT_TIMEOUT` | ❌ 本地降级 | 静默超上限，降级硬中断 |

本地内存注册表 `ActiveTaskRegistry`：

```java
ConcurrentHashMap<String, ActiveTask> registry = new ConcurrentHashMap<>();

enum TaskMode { RUNNING, SILENT, CANCELLING, FINISHED }

class ActiveTask {
    String requestId;
    String userId;
    String sessionId;
    ChatPipelineContext ctx;              // 用于 ctx.interrupt(...)
    Thread workerThread;                  // 诊断用
    long startedAt;
    volatile StreamingHandle streamingHandle;  // 仅流式调用期间非空
    volatile TaskMode mode = TaskMode.RUNNING;
    volatile boolean muted;               // 静默开关
    volatile long silentSince;
}
```

`streamingHandle` / `mode` / `muted` / `silentSince` 必须 `volatile`：Pub/Sub 回调线程与 Reactor 线程写，工作线程读。

#### 3.3.4 两种中断意图（核心概念）

| 维度 | USER_STOP | CLIENT_DISCONNECT |
|---|---|---|
| 触发 | 用户点「停止生成」 | 关网页、断网、锁屏 |
| 用户意图 | 立刻停下，别浪费钱 | 帮我生成完，回头再看 |
| 中断类型 | 硬中断 | 软中断（静默） |
| 对 LLM | 立刻 `streamingHandle.cancel()` | 不切断，继续生成 |
| 对上游推送 | 停止 | 停止（连接已断） |
| 对下游落库 | 不保存残缺回答 | 静默写入完整回答 |
| 并发额度/会话锁 | 立刻释放 | 自然结束后释放 |

一句话：**USER_STOP 是「取消任务」，CLIENT_DISCONNECT 是「取消订阅，但任务继续跑」。**

CLIENT_DISCONNECT 不广播：信号来自本实例的 SSE 连接，pipeline 必在同实例，本地直调即可：

```java
return sink.asFlux()
        .doOnCancel(() -> registry.silence(requestId, "CLIENT_DISCONNECT"));
```

#### 3.3.5 静默模式实现

静默不需要累积器：`onCompleteResponse` 拿到的 `AiMessage` 本身就是完整回答，`ChatMemorySaveStage` 会正常落库。只需让 token 不再推给前端：

```java
AtomicBoolean muted = new AtomicBoolean(false);
Consumer<String> output = token -> {
    if (!muted.get()) {
        sink.tryEmitNext(token);
    }
};
ctx.setAttribute(ChatPipelineContext.STREAM_TOKEN_CONSUMER, output);
```

约束：

- **不要**把 `STREAM_TOKEN_CONSUMER` 置为 `null` 表示静默（会让下一轮工具调用退化为非流式）；
- **不要**在 `doOnCancel` 里直接改 `ctx.attributes`（`HashMap` 非线程安全）；
- 静默必须有上限：超过 `maxSilentSeconds` 降级为硬中断，否则退化成资源泄漏。

#### 3.3.6 状态机

```
                USER_STOP
   RUNNING ────────────────────> CANCELLING ────> FINISHED(CANCELLED)
      │                                              ↑
      │ CLIENT_DISCONNECT                            │
      └──────────────> SILENT ──(自然完成)──> FINISHED(COMPLETED)
                          │
                          └──(超过 maxSilentSeconds)──> CANCELLING
```

| 当前 | 收到 USER_STOP | 收到 CLIENT_DISCONNECT | 收到 SILENT_TIMEOUT |
|---|---|---|---|
| `RUNNING` | → `CANCELLING` | → `SILENT`（`muted=true`） | 忽略 |
| `SILENT` | → `CANCELLING` | 忽略（已静默） | → `CANCELLING` |
| `CANCELLING` | 忽略 | 忽略 | 忽略 |
| `FINISHED` | 忽略 | 忽略 | 忽略 |

#### 3.3.7 两级取消机制（仅 USER_STOP）

| 级别 | 手段 | 生效时机 | 延迟 |
|---|---|---|---|
| L1 | `ctx.interrupt("用户主动取消")` | 下一个 stage 边界 / 工具循环下一轮 | 一次模型调用 |
| L2 | `streamingHandle.cancel()` | 立即关闭 HTTP 流 | 亚秒级 |

必须两级都做：只做 L1 达不到秒级；只做 L2 在非流式或工具轮次之间没有中断能力。

L2 前提：必须覆写 LangChain4j 的 `onPartialResponse(PartialResponse, PartialResponseContext)` 重载才能拿到 `StreamingHandle`。

#### 3.3.8 线程与资源所有权

| 动作 | 执行线程 | 允许 |
|---|---|---|
| 注册/注销任务 | 工作线程 | ✅ |
| `ctx.interrupt()` / `handle.cancel()` | 订阅回调线程 | ✅ 只写 volatile/原子字段 |
| `muted = true` | Reactor 线程（`doOnCancel`） | ✅ |
| `concurrentLimitService.release()` | 工作线程 | ❌ 禁止回调线程 |
| `unlockSession()` | 工作线程 | ❌ 绝对禁止回调线程 |

单一所有权原则：**状态标记可以多线程写，资源释放只归工作线程。**

#### 3.3.9 已知风险与对策

| 风险 | 对策 |
|---|---|
| `cancel()` 后回调序列未约定，`future.get()` 可能永久阻塞 | `future.get(timeout)`；主动 `completeExceptionally(CancellationException)`；开工第一步先写验证用例 |
| Pub/Sub fire-and-forget 丢消息 | L1 `ai:cancel:flag` 兜底；L2 逐 token 检查 `ctx.isInterrupted()`；L3 依赖 S1 窗口 + S2 看门狗 |
| 注册表内存泄漏 | `finally` 中 `unregister`；同 requestId 覆盖告警；可选僵尸巡检 |
| 断连感知用了 `SseEmitter` 思路 | 项目实际是 `Flux` + `Sinks.Many`，用 `doOnCancel` |
| 静默期间会话锁占用更久 | 用 `maxSilentSeconds` 限制窗口，错误提示说明「上一轮回答仍在生成」 |

SSE 收尾帧：

| 场景 | 推什么 |
|---|---|
| 正常完成 | `[DONE]` |
| USER_STOP | `[CANCELLED]` + `[DONE]` |
| CLIENT_DISCONNECT / SILENT_TIMEOUT | 不推（连接已断） |

#### 3.3.10 接口

```
POST /api/pipline/cancel
{ "requestId": "8f14e45f-...", "intent": "USER_STOP" }

Resp: { "code": 200, "data": { "accepted": true, "local": true } }
```

- 返回 200 而非 404：广播语义下发布者不知道任务在哪台机器，本实例未命中不代表失败；
- `local` 表示本实例是否持有任务，排查用；
- 重复取消幂等；`requestId` 为空返回 400；
- 只接受 `USER_STOP`。

### 3.4 S4 RAG 混合检索（基础设施完成，核心未实现）

**业务背景**：纯向量检索对精确关键词（产品型号 `X-990A`、人名、版本号）效果差：embedding 把字面信息语义化，型号类 token 没有稳定语义，容易被语义相近的噪音淹没。

**需求**

1. **双写双索引**：分块后同时写 Chroma（向量）与 ES（倒排）；
2. **双路检索**：查询同时发起向量检索与 ES BM25；
3. **RRF 融合**：按名次融合两路结果，返回 Top-K。

**方案**

- ES 索引 `vllmpt_knowledge_chunks`，启动时幂等创建；
- `content`：`ik_max_word` 写入 / `ik_smart` 查询；`fileName`、`taskId`、`source` 为 keyword；`chunkIndex` integer；`createdAt` epoch_millis；
- 文档 id：`taskId:chunkIndex`，重复写入覆盖，天然幂等；
- 双写门面 `DualIndexWriter`（先 Chroma 后 ES，任一失败抛异常，由上层重试兜底）；
- 检索：每路取 `topK*2` 候选 → RRF `score = Σ 1/(60 + rank)`，rank 从 1 开始 → Top-K；
- BM25 路失败返回空列表，由向量路兜底（允许一路失败）；
- 客户端 8.11.4 / 服务端 8.11.0 必须同 minor，`pom.xml` 锁定 `elasticsearch-rest-client` 版本。

**验收**

- 同一份文件入库后 Chroma 与 ES 都能查到分块；
- `GET vllmpt_knowledge_chunks/_count` 与分块数一致；
- 专有名词查询命中优于纯向量检索；
- 同一 `taskId + chunkIndex` 重复写入不产生重复文档；
- 能解释为什么 RRF 不需要分数归一化。

### 3.6 S6 百 MB 大文件 RAG 异步入库（基础设施完成，核心未实现）

**业务背景**：200MB PDF 同步处理会超时，必须异步化，并让前端看到「解析中 30% → 分块中 60% → 向量化中 90% → 完成」。

**需求**

1. **MQ 拓扑**：按阶段拆分 Topic / 消费组（解析 → 向量化），Tag 过滤阶段路由；
2. **进度追踪**：消费者写 Redis 进度，通过 SSE/轮询推送给前端；
3. **失败处理**：向量化失败重试耗尽进 DLQ 并告警；
4. **超时处理**：超过 `stageTimeoutSeconds` 的任务判定失败；
5. **幂等**：重复消费不重复入库、不篡改已完结任务。

**方案**

- 提交：校验 temp 桶文件 → 归档 data 桶 → 建台账 → 发解析消息 + 超时检查延迟消息 → 立即返回 `taskId`；
- MQ：RocketMQ（NameServer 9876 / Broker 10911 / Dashboard 8180）；
- 进度：Redis Hash `ai:file:task:progress:{taskId}`，字段 `status/stage/percent/message/updatedAt`，写入用 `StringCodec`，每次写续期 `progressTtlSeconds`；
- 台账：MySQL `ai_file_parse_task`，`status` 仅 `PENDING/SUCCESS/FAILED`，中间态只存 Redis；
- 幂等：`markSuccess`/`markFailed` 只允许 `PENDING→终态`；ES 文档 id 幂等；向量入库按 taskId 去重；
- DLQ：独立消费组监听 `%DLQ%{group}`，处理 = `markFailed` + `AlertService.alert`；
- 超时：延迟消息（level 17/18）到点比对 Redis `updatedAt`，或定时扫描（二选一）。

**SSE 进度接口（待开发，建议规格）**

```
GET /api/file/task/{taskId}/progress
Accept: text/event-stream

{ "taskId":"xxx","status":"RUNNING","stage":"EMBEDDING","percent":90,
  "message":"向量化中...","updatedAt":1760000000000 }
```

连接后立即推送快照，`SUCCESS`/`FAILED` 后推 `[DONE]` 并关闭。

**验收**

- 上传 200MB PDF 立即返回 `taskId`；
- Redis 能看到进度流转，SSE 能实时推送；
- 完成后台账 `SUCCESS` 且 `chunk_count` 回填；
- 模拟失败：重试耗尽 → DLQ → 台账 `FAILED` → 告警；
- 重复消费不重复入库、不改已完结任务；
- 超时任务被判定失败；
- Dashboard 能看到 Topic、消费组、死信 Topic；
- 刷新页面后能通过台账 + Redis 恢复进度。

| 模块 | 状态 |

### 3.7 S7 Agent 工具异步 RPC（规划）

## 4. 通用审批平台需求

### 4.1 目标与范围

平台需同时支撑请假、差旅费、会议室申请，以及未来的采购、用印、合同、加班、转正等审批。因此不能把「请假」写进引擎，抽象为：

```
流程模板 + 表单 Schema + 审批节点 + 任务 + 抄送 + AI 扩展点
```

业务只负责：表单字段定义、业务校验、业务数据落库、事实提取、审批完成后的业务动作。

两个 AI 能力：

| | A：AI 填表 | B：AI 审批决策 |
|---|---|---|
| 输入 | 自然语言 + 表单 Schema | 审批实例 + 业务事实 + 规则 |
| 输出 | 草稿 / 缺失字段追问 | 通过 / 拒绝 / 转人工 |
| 位置 | 通用 `ApprovalToolProvider` | `AI_DECISION` 节点 |
| 失败 | 继续追问 | 转人工，绝不自动批 |

业务层：biz/leave、biz/travel、biz/meeting

### 4.3 领域模型与状态机

核心对象：`ApprovalTemplate`、`ApprovalTemplateNode`、`ApprovalInstance`、`ApprovalTask`、`ApprovalRecord`、`ApprovalCc`、`ApprovalAiDecision`、`ApprovalBizDraft`。

实例状态：

```
DRAFT ──提交──▶ RUNNING ──全部通过──▶ APPROVED
                   ├──任一节点拒绝──▶ REJECTED
                   ├──发起人撤回────▶ CANCELED
                   └──管理员终止────▶ TERMINATED
REJECTED ──重新提交──▶ RUNNING（新实例，parent_instance_id 关联）
```

任务状态：`WAITING / PENDING / APPROVED / REJECTED / SKIPPED / TRANSFERRED / CANCELED`。

节点类型：

| 类型 | 行为 |
|---|---|
| `START` | 入口，直接通过 |
| `APPROVAL` | 解析审批人并生成任务，等待人工处理 |
| `AI_DECISION` | AI 决策；P0 未接入插件时固定转人工 |
| `CC` | 写抄送记录后立即继续，不阻塞 |
| `CONDITION` | 条件节点；引擎对任意节点都支持条件跳过 |
| `END` | 结束，实例置为 `APPROVED` |

审批人类型：`USER` / `ROLE` / `DIRECT_MANAGER` / `DEPT_HEAD` / `FORM_FIELD` / `INITIATOR`。

审批模式：

| 模式 | 任务初始化 | 推进条件 |
|---|---|---|
| `ANY`（或签） | 全部 `PENDING` | 任意一人通过，其余取消 |
| `ALL`（会签） | 全部 `PENDING` | 全部通过才推进；任一拒绝即拒绝 |
| `SEQUENTIAL` | 首个 `PENDING`，其余 `WAITING` | 前一个通过后激活下一个 |

审批人解析失败：不允许自动通过，转 HR/管理员并记录 `ASSIGNEE_NOT_FOUND` 告警。

条件 DSL（JSON 求值，不使用 SpEL，避免表达式注入）：

```json
{"op":"AND","children":[
  {"field":"amount","op":"GT","value":5000},
  {"field":"city","op":"IN","value":["上海","北京"]}
]}
```

支持：`AND/OR/NOT`、`EQ/NE/GT/GTE/LT/LTE`、`IN/NOT_IN/CONTAINS/EXISTS`。

模板版本：实例创建时固定 `template_id + template_version`；修改/下线模板不影响运行中实例。

### 4.6 功能 A：通用 AI 填表（P2 已实现）

**表单 Schema**：`approval_template.form_schema`，示例：

```json
{
  "bizType": "TRAVEL_EXPENSE",
  "title": "差旅费申请",
  "fields": [
    {"key":"destination","label":"目的地","type":"string","required":true},
    {"key":"estimatedAmount","label":"预计金额","type":"number","required":true,"min":0}
  ]
}
```

**通用工具**（所有业务共用，`@AiTool(groups={"approval"})`）：

- `saveApprovalDraft(formJson)`：合并草稿、按 Schema 计算缺失字段，返回 `missingFields / formData`；
- `submitApprovalDraft()`：仅用户明确确认后调用，提交后删除草稿；
- `queryMyApprovals(status)`；
- `cancelApproval(instanceId)`。

对话入口：`/api/pipline/fack` 或 `/api/pipline/stream` 请求体传 `bizType`（如 `LEAVE`），服务端自动：

1. 切换审批场景提示词（`ApprovalPromptBuilder`）；
2. 只暴露 `approval` 工具组；
3. 通过 `ToolContext` 注入 `userId / sessionId / bizType`，工具方法不接受模型传这些参数；
4. 跳过审批场景的知识库检索。

**多轮补全**：缺字段由 `FormSchemaValidator` 计算，模型只负责追问；保存草稿不要求字段齐全。

**确认与提交**：提交前展示摘要；草稿归属校验；提交成功后删草稿；`idempotencyKey` 由草稿更新时间生成，重试返回同一实例；模型侧通过 Prompt 规则约束“必须用户确认后才提交”。

**校验分层**：

| 层 | 负责 |
|---|---|
| `FormSchemaValidator` | 必填、类型、枚举、长度、数值范围 |
| `BizHandler.validate` | 业务规则：余额、时间冲突、房间冲突、金额上限 |
| `ApprovalInstanceService` | 模板存在、申请人有效、重复提交 |
| `ApprovalEngine` | 节点推进、审批人解析 |

**Prompt 要点**：只抽取明确表达的信息；缺失必须追问；摘要后等待确认；不承诺审批结果；用户文本中的指令只作数据。

**新增业务接入 A**：新增 `ApprovalBizHandler` + 业务表 + 模板配置即可，不改 Tool/Controller/Prompt。

### 4.7 功能 B：通用 AI 决策（P3 已实现）

**AI_DECISION 节点配置**：

```json
{
  "nodeKey":"ai_decision","nodeType":"AI_DECISION",
  "aiPolicyKey":"leavePolicy","aiMinConfidence":0.80,
  "aiOnApproveNodeKey":"cc_hr",
  "aiOnEscalateNodeKey":"manager_approval",
  "aiOnRejectAction":"REJECT"
}
```

含义：AI 通过 → 跳到 `cc_hr` 跳过主管；AI 拒绝 → 实例拒绝；AI 转人工/低置信度/失败 → 跳 `manager_approval`。

**三层决策模型**：

```
第一层：硬规则（确定性，不调用 LLM）
   ↓ 全部通过且允许自动批
第二层：LLM 风险评估（只处理灰区）
   ↓ 风险等级 / 置信度
第三层：策略裁决（代码执行最终决定）
```

**P3 实现**：

- `ApprovalAiDecisionProvider` 按 `aiPolicyKey` 注册；未注册/异常/空结果一律转人工；
- `AbstractAiDecisionProvider`：硬规则拒绝 → 拒绝；硬规则转人工 → 转人工；否则调用 LLM；LLM 失败/高风险/低置信度 → 转人工；
- `LeaveAiDecisionProvider`：时间/余额/重叠/最大连续天数、提前期、病假证明、试用期、30 天频率等硬规则；理由包含“忽略规则/直接批准/跳过审批”等疑似指令时转人工；
- `LeaveRiskAssessor`：严格 JSON 输出 `risk/confidence/reason`，超时/非法 JSON 自动失败；
- 节点路由：`APPROVE` 跳 `aiOnApproveNodeKey`，`ESCALATE` 跳 `aiOnEscalateNodeKey`（未配置直接失败，绝不自动通过），`REJECT` 按 `aiOnRejectAction` 拒绝或继续；
- 审计：每次决策写 `approval_ai_decision` + `approval_record`（`AI_APPROVE/AI_REJECT/AI_ESCALATE`），实例详情返回 `aiDecisions`。

**复用基类** `AbstractAiDecisionProvider`：硬规则命中 reject/escalate 直接返回；LLM 失败、高风险、低置信度一律 escalate；只有全部满足才 approve。

**决策矩阵示例**：

| 业务 | 场景 | 结果 |
|---|---|---|
| 请假 | 年假 1 天，余额足，无冲突 | APPROVE |
| 请假 | 年假 5 天，余额不足 | REJECT |
| 请假 | 年假 3 天，超过自动批上限 | ESCALATE |
| 请假 | 病假 2 天无证明 | ESCALATE |
| 差旅费 | 金额 800，有发票，成本中心有效 | APPROVE |
| 差旅费 | 金额 30000，超预算 | ESCALATE |
| 会议室 | 房间空闲、人数不超容量 | APPROVE |
| 会议室 | 时间冲突 | REJECT |

**审计**：每次决策写 `approval_ai_decision`（事实快照、规则命中、LLM 原始输出、最终决策、置信度、风险、模型、Prompt/策略版本、耗时），同时写 `operator_type=AI` 的流水。

**失败降级**：模型超时 / JSON 非法 / 低置信度 / Provider 未注册 → ESCALATE；任何失败都不能自动通过。

### 4.8 多级审批、抄送与通知

- 引擎按 `sort_order` 线性推进，条件不满足直接跳过；`visited` 集合检测环；
- ANY：首个通过后取消同节点其他任务；
- ALL：全部通过才推进，任一拒绝即拒绝；
- SEQUENTIAL：逐个激活，最后一个通过后推进；
- 驳回：实例 `REJECTED`，取消同节点其他待办；
- 撤回：仅申请人且 `RUNNING`，实例 `CANCELED`，写 `WITHDRAW` 流水；
- 重新提交：创建新实例，`parent_instance_id` 关联旧实例，`submit_count+1`，写 `RESUBMIT` 流水；
- CC：不生成任务、不阻塞；`approval_cc` 唯一键保证幂等；当前已实现 `INBOX` 通知渠道（写 `approval_notification` 发件箱），钉钉/飞书/邮件渠道通过 `ApprovalNotifyChannel` 扩展；
- 通知：CC 站内信在抄送节点内幂等写入 `approval_notification`；外部渠道通过发件箱重试，失败不回滚审批；
- 关键业务动作（余额扣减）在审批事务内完成，失败回滚；会议室提交时对会议室行加锁并复核时间冲突；`applyResult` 与监听器必须幂等。

### 4.9 第一批业务落地

#### 4.9.1 请假

表单：`leaveType`（ANNUAL/SICK/PERSONAL/COMP_TIME）、`startTime`、`endTime`、`reason`、`attachmentUrls`；`leaveDays` 由服务端计算。

业务规则：

- 时区统一 `Asia/Shanghai`；相对日期由服务端解析；
- 工作日 = 周一至周五排除节假日，`WORKDAY` 类型的周末算工作日；半天计 `0.5`；
- 截止/开始时间落在 12:00 前后区分上午/下午；
- 时间非法、开始时间在过去、与已有 `PENDING/APPROVED` 重叠、余额不足 → 拒绝；
- 病假超 1 天无证明 → 要求补材料或转人工；
- 试用期、部门冻结期、近 30 天频繁请假、超过自动批上限 → 转人工；
- 只对客观事实自动拒绝；理由不充分、语气可疑等一律转主管；
- `AUTO_REJECT` 提供一次人工复核入口（`action=APPEAL`）。

策略默认值（P3 在代码 `LeavePolicy` 中定义，后续可迁 `leave_policy` 表）：

| 类型 | 自动批 | 自动批上限 | 最大连续 | 提前天数 | 需附件 | 30 天上限 | 最低置信度 |
|---|---|---|---|---|---|---|---|
| ANNUAL | 是 | 2 天 | 5 天 | 1 | 否 | 3 | 0.80 |
| SICK | 是 | 1 天 | 3 天 | 0 | 是 | 3 | 0.85 |
| PERSONAL | 否 | - | 3 天 | 1 | 否 | 2 | 0.90 |
| COMP_TIME | 是 | 1 天 | 3 天 | 1 | 否 | 3 | 0.85 |

## 5. 非功能需求

### 5.1 身份与权限

- 支持 `Authorization: Bearer <jwt>`，JWT 只携带用户 ID，角色在请求时从 `sys_user_role` 读取；
- 开发期：`X-User-Id` 请求头指定用户；`app.identity.default-user-enabled=true` 时不传默认用户 1；
- 生产：关闭默认用户，`app.jwt.dev-token-enabled=false`，由统一登录服务签发 JWT；
- 公开路径仅限 Swagger、`/actuator/health|info`、开发 token 接口与 `/error`；其余接口必须认证；
- 审批权限：查看实例 = 申请人 / 任务审批人 / 抄送接收人；审批操作 = 仅任务归属人且 `PENDING`；撤回 = 仅申请人；重新提交 = 仅申请人且父实例 `REJECTED`；
- 模板创建/编辑/发布/下线要求 `ADMIN` 角色，演示数据中用户 5 具备 ADMIN。

### 5.2 并发与一致性

- 实例级 `SELECT ... FOR UPDATE` 串行化同一实例审批动作；
- 实例 `version` 乐观锁，冲突返回 409；
- 会签剩余任务使用锁定读，避免 REPEATABLE READ 旧快照；
- `task_key` 唯一键保证任务幂等；`approval_cc` 唯一键保证抄送幂等；
- Redis 只做加速与幂等，不参与最终状态判定；
- 提交幂等：Redis `trySet(PENDING, 5min)`，已完成返回原实例 ID，处理中返回 429，事务回滚释放占位。

### 5.3 可靠性降级

| 故障 | 行为 |
|---|---|
| Redis 单号计数不可用 | 降级为日期 + 6 位随机数，`uk_instance_no` 兜底 |
| Redis 幂等键不可用 | 跳过幂等校验并 WARN，主链路继续 |
| ES BM25 失败 | 返回空列表，向量路兜底 |
| Chroma 不可用 | 对话降级为通用提示词 |
| MQ 发送失败 | 台账 `markFailed`，避免幽灵任务 |
| 通知发送失败 | 发件箱重试，不回滚审批 |

### 5.4 可观测性

- 全链路日志带 `requestId` / `taskId` / `instanceId`；
- 审批流水、AI 决策快照可追溯；
- Actuator 暴露 health/metrics/prometheus；
- AI 决策指标：`approval.ai.decision{decision=APPROVE|REJECT|ESCALATE}` 计数、`approval.ai.decision.latency{decision}` 耗时；
- 灰度：`approval.ai.rollout-percent` 按实例 ID 稳定分桶，未命中的实例一律转人工；
- 自动批率 = APPROVE / 全部 AI 决策；升级率 = ESCALATE / 全部 AI 决策；平均耗时取 timer 的 `sum/count`；
- 文件任务失败触发 `AlertService`（未配置 webhook 时只打 ERROR）。

### 5.5 兼容性

- 模板版本隔离：运行中实例固定 `template_id + template_version`；
- 新增业务只写 SPI + 模板，不改引擎；
- 模型可替换（OpenAI 兼容协议），结构化输出不支持时降级 Prompt + Jackson 解析。

## 6. 验收标准

### 6.1 审批平台

- [ ] 新增审批业务只需 Handler + 模板，不改引擎；
- [ ] 请假、差旅费、会议室都能跑通；
- [ ] 多级审批与条件跳过正确；
- [ ] ANY/ALL/SEQUENTIAL 行为符合定义；
- [ ] 驳回、撤回、重新提交状态正确；
- [ ] AI 自动批只在授权范围内，失败必转人工；
- [ ] 抄送/通知可配置、可重试；
- [ ] 节点流转与 AI 决策可追溯；
- [ ] 模板升级/下线不影响运行中实例；
- [ ] 非审批人操作 403，申请人不能审批自己的单。

### 6.2 通用能力

- [ ] 并发超限 429，结束后额度归零；
- [ ] 同会话并发 409 / `[ERROR]`；
- [ ] 混合检索专有名词命中优于纯向量；
- [ ] 200MB 文件异步入库不阻塞，进度可追踪，失败进 DLQ 并告警。

## 7. 风险与边界

| 风险 | 应对 |
|---|---|
| 过度设计 | v1 只做线性 + 条件跳过，不做完整 BPMN |
| 业务侵入引擎 | core 只依赖 SPI，ArchUnit 禁止反向依赖 |
| AI 误批 | 授权信封 + 硬规则 + 人工抽查 + 申诉 |
| Prompt 注入 | 事实来自数据库，规则不读用户文本 |
| 通知丢失 | 事务后事件 + 发件箱重试 |
| 模板变更影响运行中实例 | 实例固定模板版本 |
| 审批人缺失 | 转 HR/管理员，禁止自动通过 |
| 余额/房间超卖 | 条件更新 + version + 唯一键 |
| 主动取消阻塞工作线程 | `future.get` 超时 + 主动 `completeExceptionally` |
| 静默模式资源泄漏 | `maxSilentSeconds` 上限降级 |

明确不做：

- 不做通用 BPMN 引擎；
- 不做复杂并行网关（v2 再评估）；
- 不允许 LLM 直接改审批状态；
- 第一版不接入飞书/钉钉原生审批 API；
- 不做语义缓存（需 Redis Stack 向量模块，项目已用 Chroma，避免重复建设）。
