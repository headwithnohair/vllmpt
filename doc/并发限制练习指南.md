# Redis ZSet 单用户并发推理限制 · 手把手练习指南

> 目标：自己动手实现「同一用户最多 N 个并发推理任务」的 Redis 限流。
> 代码骨架已经写好，你只需要补 5 个 TODO。参考实现放在文末附录，**建议自己写完再对照**。

---

## 0. 这个场景要解决什么问题

大模型推理（尤其 72B 级别）极其消耗 GPU。如果不限制单用户的并发请求数，
一个写错代码的客户端同时发起 100 个 SSE 流式对话，就会打满显存、拖垮队列，影响其他用户。

**核心需求**：同一个 userId 同一时间最多只能有 N 个（本项目默认 3 个）正在进行的推理任务。

**为什么用 ZSet 而不是计数器**：
计数器只能存"当前有几个"，无法处理"某个任务卡死/断连后额度永远不释放"的问题；
ZSet 用 `score = 发起时间戳` 记录了每个任务的生命周期，可以按时间窗口自动清理僵尸任务。

## 1. 数据结构设计（先想清楚再写代码）

| 项 | 取值 | 说明 |
|---|---|---|
| key | `ai:concurrent:{userId}` | 本项目 userId 复用 `sessionId`，缺失时兜底 `anonymous` |
| member | `requestId`（UUID） | **绝不能是 sessionId**，原因见下 |
| score | 发起时间戳（毫秒） | 用于按时间窗口清理 |
| 窗口 | `window-seconds`（默认 300s） | score 早于 `now - window` 的 member 视为僵尸，自动清理 |
| key TTL | `key-ttl-seconds`（默认 600s） | 兜底过期，比窗口大，保证正常计数不被误删 |

### 为什么 member 不能用 sessionId？

因为 `sessionId` 已经是 **key 的一部分**了。同一个 session 的第二个请求会用同样的 member 再 `ZADD` 一次，
Redis 会**更新 score 而不是新增一个元素**，`ZCARD` 永远是 1 → 限制永远不触发。

### 为什么窗口要设 300s 而不是 todo.txt 里写的 60s？

`ChatAgentStage` 最多有 10 轮工具调用循环，单次推理可能远超 60s。
如果窗口设小了，慢请求会被误判为"僵尸"清理掉，实际并发就会突破 limit（超卖）。
**口诀：窗口必须大于最慢一次推理的耗时。**

## 步骤二：写 Lua 脚本（TODO 1）

**文件**：`src/main/java/org/albedo/vllmpt/module/chat/service/ConcurrentLimitService.java`
**位置**：常量 `LUA_ACQUIRE` 的文本块里（目前只有一行 `-- TODO`）

### 入参约定（已经在注释里写好了）

```
KEYS[1] = ai:concurrent:{userId}
ARGV[1] = nowMs   当前时间戳（毫秒）
ARGV[2] = windowMs   窗口大小（毫秒）
ARGV[3] = limit      并发上限
ARGV[4] = requestId  本次请求 ID
ARGV[5] = ttlSec     key 兜底过期（秒）
```

### 必须按顺序完成 4 件事

1. `ZREMRANGEBYSCORE key 0 (now - window)` —— 清掉僵尸 member
2. `ZCARD key` —— 统计当前活跃数
3. `count >= limit` → `return 0`（拒绝）
4. 否则 `ZADD key now requestId` + `EXPIRE key ttlSec` → `return 1`（放行）

### 提示

- `redis.call(...)` 的返回值就是命令的返回值，`ZCARD` 直接返回数字，`ZADD` 返回新增个数
- **所有 ARGV 在 Lua 里都是字符串**，数字比较前要 `tonumber(ARGV[x])`
- 别用 `KEYS` 的 pattern 匹配，这里是精确的单 key

### 单独验证这个 Lua（不用启 Java，推荐做一次）

在写 Java 之前，先用 redis-cli 把脚本逻辑跑通：

```powershell

local limit=tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local c = redis.call('ZCARD', key)
if c >= limit then return 0 end
redis.call('ZADD', key, now, ARGV[4])
```

## 步骤三：实现 tryAcquire（TODO 2）

**签名**：`public boolean tryAcquire(String userId, String requestId)`

### 必须做到的 5 点

1. key 用 `RedisKey.concurrent(userId)`
2. `now` 用 `System.currentTimeMillis()`
3. 用 `redissonClient.getScript(...)` 拿脚本对象，`eval(...)` 执行：
   - `Mode` 用 `RScript.Mode.READ_WRITE`（脚本里有写操作）
   - 返回类型用 `RScript.ReturnType.LONG`
   - keys 传 `List.of(key)`
   - values 依次传 now / windowMs / limit / requestId / ttlSec
4. 阈值从 `props` 取：`props.getLimit()`、`props.getWindowSeconds() * 1000L`、`props.getKeyTtlSeconds()`
5. 结果为 `1L` → `return true`；否则打 `warn` 日志（带 userId / requestId）并 `return false`

### 三个必踩的坑

| 坑 | 现象 | 原因 / 解法 |
|---|---|---|
| **没传 StringCodec** | `ZCARD` 永远是 0，限制永不触发 | `getScript()` 默认用全局 codec（Kryo5），String 会被写成二进制。必须 `getScript(StringCodec.INSTANCE)` |
| **参数类型不统一** | Lua 里 `tonumber` 拿到 nil，脚本报错 | 所有 ARGV 统一 `String.valueOf(...)` 传，包括数字 |
| **找不到 `ReturnType.INTEGER`** | 编译不过 | Redisson 4.4.0 已改名为 `LONG`（可用 `javap -classpath <redisson.jar> 'org.redisson.api.RScript$ReturnType'` 自查） |

> 记忆点：**codec 决定 key/value 写进 Redis 长什么样**。
> 用错 codec，`redis-cli` 里看到的 member 会是一堆 `\xac\xed...`，而不是可读的 UUID。
> 这一步做完可以用 `ZRANGE ... 0 -1` 肉眼确认 member 是可读字符串。

## 步骤四：实现 release（TODO 3）

**签名**：`public void release(String userId, String requestId)`

### 要点

1. `redissonClient.getScoredSortedSet(RedisKey.concurrent(userId), StringCodec.INSTANCE).remove(requestId)`
2. 外面套 `try / catch`，异常只打 `error` 日志并**吞掉**

### 为什么要吞异常？

`release` 一定在 `finally` 里被调用。如果这里抛出异常，会**覆盖掉真正的业务异常**
（比如 pipeline 失败的原因），排查问题时会被误导。释放失败不是致命问题，靠窗口兜底即可。

### 为什么不需要考虑幂等？

`ZREM` 删一个不存在的 member 返回 0，不报错，天然幂等。重复 release 安全，不用加锁。

## 步骤七：改造 `/stream`（TODO 5）

同一个文件，`TODO [步骤6-1]` / `TODO [步骤6-2]`。

### 与 `/fack` 的唯一区别（也是整个场景最核心的坑）

**`tryAcquire` 必须写在 `return sink.asFlux()` 之前。**

原因：一旦方法返回 `Flux`，Spring 就吐出了响应头 `HTTP 200 + Content-Type: text/event-stream`，
此后**再也无法把状态码改成 429**，最多只能往里推一帧 `[ERROR] ...` 文本。

所以顺序必须是：

```
buildContext → 生成 requestId → tryAcquire → [失败: 抛 429] → 注入 STREAM_TOKEN_CONSUMER → runAsync → return sink.asFlux()
                    ↑ 同步完成                                                                    ↑ 异步执行
```

### 另外两点

- `release` 放在 `CompletableFuture.runAsync` 内部的 `finally`（`TODO [步骤6-2]`）
- **客户端断连时不要释放**。此时 pipeline 还在跑，提前释放会让实际并发超过 limit；
  靠 ZSet 窗口 + `EXPIRE` 兜底自动清理就够了

## 附录：参考实现（**自己写完再看**）

### Lua（`LUA_ACQUIRE`）

```lua
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count >= limit then
    return 0
end

redis.call('ZADD', key, now, ARGV[4])
redis.call('EXPIRE', key, ARGV[5])
return 1
```

### `tryAcquire`

```java
public boolean tryAcquire(String userId, String requestId) {
    String key = RedisKey.concurrent(userId);
    long now = System.currentTimeMillis();

    Long result = redissonClient.getScript(StringCodec.INSTANCE).eval(
            RScript.Mode.READ_WRITE,
            LUA_ACQUIRE,
            RScript.ReturnType.LONG,
            List.of(key),
            String.valueOf(now),
            String.valueOf(props.getWindowSeconds() * 1000L),
            String.valueOf(props.getLimit()),
            requestId,
            String.valueOf(props.getKeyTtlSeconds()));

    boolean acquired = result != null && result == 1L;
    if (!acquired) {
        log.warn("并发额度不足: userId={}, requestId={}, limit={}", userId, requestId, props.getLimit());
    }
    return acquired;
}
```

### `release`

```java
public void release(String userId, String requestId) {
    try {
        RScoredSortedSet<String> zset =
                redissonClient.getScoredSortedSet(RedisKey.concurrent(userId), StringCodec.INSTANCE);
        zset.remove(requestId);
    } catch (Exception e) {
        log.error("释放并发额度失败: userId={}, requestId={}", userId, requestId, e);
    }
}
```

### `/fack` 的 acquire + release

```java
// acquire（放在 executor.execute 之前）
if (!concurrentLimitService.tryAcquire(userId, requestId)) {
    throw new BusinessException(CODE_TOO_MANY_CONCURRENT, "您的并发请求过多，请稍后重试");
}

try {
    executor.execute(chatPipeline, ctx);
    // ... 原有返回逻辑
} finally {
    concurrentLimitService.release(userId, requestId);
}
```

### `/stream` 的 acquire + release

```java
// acquire（必须在 return sink.asFlux() 之前）
if (!concurrentLimitService.tryAcquire(userId, requestId)) {
    throw new BusinessException(CODE_TOO_MANY_CONCURRENT, "您的并发请求过多，请稍后重试");
}

// ...

    try {
        executor.execute(chatPipeline, ctx);
        // ...

        sink.tryEmitError(e);

        concurrentLimitService.release(userId, requestId);

});

return sink.asFlux();
```

## 加餐：可以继续练的方向

1. **换成 `RLock` 实现**：用 `redissonClient.getLock("lock:concurrent:" + userId)` 包住
   `ZCARD` + `ZADD` 两步，和 Lua 版对比 RTT、吞吐和代码复杂度。
2. **加滑动窗口限流**：同一个 ZSet 结构就能做"每分钟最多 10 次请求"，
   把判限逻辑从 `ZCARD` 换成 `ZCARD` + 窗口设为 60s 即可。
3. **多级限流**：本地 `Semaphore` 挡一层（省 Redis 网络开销）+ Redis ZSet 挡全局一层。
