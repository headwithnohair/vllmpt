## 一、任务目标

### 1.1 业务背景

用户上传 200MB 的 PDF，后端如果**同步**处理会超时。必须异步化，且前端需要看到实时进度：

```
解析中(30%) -> 分块中(60%) -> 向量化中(90%) -> 完成
```

### 1.2 核心需求

1. **设计 MQ 拓扑**：按阶段拆分 Topic / 消费组（解析 → 向量化），结合 Tag 过滤实现阶段路由。
2. **进度追踪**：消费者处理完一个阶段，将进度写入 Redis，并通过 SSE/WebSocket 推送给前端。
3. **失败处理**：如果向量化阶段失败（如 Chroma 宕机），消息进入死信队列（DLQ），并触发告警。

### 1.3 技术考点（RocketMQ 版）

| 考点 | RocketMQ 对应机制 | 提示 |
|------|------------------|------|
| 路由机制 | Topic / Tag 过滤 + MessageQueue 分片 | `syncSend("topic:tag", msg)`；消费者 `selectorExpression` 按 Tag 过滤 |
| 发送可靠性 | 同步发送判 `SendResult.sendStatus`；异步用 `SendCallback` | `SEND_OK` 才算成功；`FLUSH_DISK_TIMEOUT` 等要处理 |
| 消费可靠性 | 返回 `ConsumeConcurrentlyStatus.RECONSUME_LATER` 触发 broker 重试 | 并发消费默认最多重试 **16 次** |
| 死信队列 | 重试耗尽后自动进入 `%DLQ%{消费者组}`，无需声明 | 用独立消费组监听 `%DLQ%` 主题做兜底处理 |
| 延迟消息 | 原生延迟级别 `MessageDelayLevel`（18 级：1s~2h），无需插件 | 用于「超时未完成」的检查消息 |

### 1.4 完成标准（自检清单）

- [ ] 上传 200MB PDF 的接口**立即返回 taskId**，不阻塞等待处理
- [ ] Redis 中能看到进度流转（`ai:file:task:progress:{taskId}`），SSE 能实时推送
- [ ] 全链路完成后，台账 `status=SUCCESS` 且 `chunk_count` 已回填
- [ ] 模拟向量化失败：消息重试耗尽 → 进入 `%DLQ%` → 台账 `FAILED` → `AlertService` 打出告警
- [ ] 重复消费同一消息：不会重复入库、不会改花已完结的任务（幂等）
- [ ] 超时任务（超过 `stageTimeoutSeconds`）被延迟消息判定并标记失败
- [ ] Dashboard（http://localhost:8180）能看到 Topic、消费组、死信 Topic
- [ ] 前端刷新后，可通过台账接口 + Redis 恢复进度展示

## 三、接口文档

### 3.1 HTTP 接口

统一返回结构：`Result<T>` = `{ "code": 200, "message": "Success", "data": ... }`

#### 【已就绪】上传与台账查询

**1. 获取预签名直传地址**（大文件主链路：前端直传 MinIO，不经后端）

```
POST /api/file/upload/UploadUrl
Body: { "fileName": "report.pdf" }
Resp: { "code":200, "data": {
        "objectName": "uuid_report.pdf",      // 后续接口都要带它
        "presignedUrl": "http://..."          // PUT 直传，5 分钟有效
      }}
```

流程：前端用 `presignedUrl` **PUT** 上传到 `vllmpt-temp` 桶 → 调后续接口通知后端。

**2. 台账详情**（前端轮询兜底 / 刷新后恢复）

```
GET /api/file/task/{taskId}
Resp: Result<FileParseTask>    // 字段见 3.4；不存在返回 code=404
```

**3. 最近任务列表**

```
GET /api/file/task/list?userId=123&limit=20     // userId 可选；limit 钳制 [1,100]
Resp: Result<List<FileParseTask>>
```

**4. 图片上传（Multipart 兜底）**

```
POST /api/file/upload/image          // form-data: file，仅图片、≤10MB
POST /api/file/upload/from-url      // { "imageUrl": "..." }
Resp: { "url": "..." }
```

**5. 提交异步解析任务**（场景6 主入口，上传完成后调它；替代同步版 /api/indexAction/file）

```
POST /api/file/task/submit
Body: {
  "objectName": "uuid_report.pdf",   // 必填：temp 桶对象名（预签名 PUT 成功后回传）
  "fileName":   "report.pdf",        // 可选：缺省取 objectName
  "etag":       "...",               // 可选：PUT 响应头中有；带上则服务端做一致性校验
  "userId":     123                  // 可选
}
Resp: { "code": 200, "data": "3f8a...c1" }   // 返回 taskId，立即返回不阻塞

// 服务端同步动作（很快）：校验 temp 文件 → 归档 vllmpt-data → 建台账
//                       → 发解析消息 + 发超时检查延迟消息
// 之后全部异步：进度看 Redis / SSE，最终状态看台账
```

#### 【已有·待异步化】当前的文件入库接口（场景6 要替代的“同步版”）

```
POST /api/indexAction/file
Body: FileUploadDTO = {
  "objectName": "...",   // temp 桶中的对象名（预签名上传后）
  "etag": "...",         // 可选，用于存在性校验
  "fileSize": 0,
  "MimeType": null,
  "businessId": null
}
Resp: Result<String>     // 返回归档后的 finalObjectName
```

> 现状：**同步阻塞**执行「校验 → 跨桶归档 → 解析 → 向量化」。
> 场景6 的目标就是把这条链路异步化：立即返回 taskId，处理逻辑搬进消费者。
> 其中「跨桶归档」由 `MinioService.FileChangeBucket()` 完成（temp → data 桶）。

#### 【待开发】进度推送（SSE）——建议规格，可自行调整

```
GET /api/file/task/{taskId}/progress
Accept: text/event-stream
```

- 连接后立即推送一次当前进度快照（读 Redis），随后每有阶段更新推送一次；
- 结束条件：收到 `SUCCESS`/`FAILED` 后推 `[DONE]` 并关闭连接；
- 约定 JSON 帧载荷（与 Redis Hash 字段一致）：

```json
{ "taskId": "xxx", "status": "RUNNING", "stage": "EMBEDDING",
  "percent": 90, "message": "向量化中...", "updatedAt": 1760000000000 }
```

#### 【参考】现有 SSE 实现（chat 模块，建议照此模式写）

```

```

- 技术栈：Reactor `Flux<String>` + `Sinks.Many` 实时推送；结束推 `[DONE]`；

### 3.3 Redis 进度数据结构约定

**Key**：`ai:file:task:progress:{taskId}`（**Hash**）

| field | 取值 | 说明 |
|-------|------|------|
| `status` | `PENDING` / `RUNNING` / `SUCCESS` / `FAILED` | 中间态 RUNNING 只存在于 Redis |
| `stage` | 如 `PARSING` / `CHUNKING` / `EMBEDDING` | 当前阶段 |
| `percent` | `0` ~ `100` | 建议 30 / 60 / 90 对应三个阶段 |
| `message` | 文案或错误摘要 | 前端展示用 |
| `updatedAt` | 毫秒时间戳 | 超时判定依据 |

注意事项：

1. **写入/读取请用 `StringCodec.INSTANCE`**，否则 redis-cli 里是乱码；
2. 每次写进度用 `expire(key, progressTtlSeconds)` 续期（兜底清理异常中断的残留 key）；
3. 建议在 `SUCCESS`/`FAILED` 时保留 key 一段时间（前端可能晚连 SSE），由 TTL 自动清理。

### 3.4 数据库表：`ai_file_parse_task`（台账）

建表脚本：`doc/sql/init_file_parse_task.sql`（已在开发库执行；`CREATE TABLE IF NOT EXISTS` 可重复跑）

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | BIGINT PK | 自增主键 |
| `task_id` | VARCHAR(64) UK | 任务 UUID（生产者生成，随消息流转） |
| `user_id` | BIGINT | 0=未登录/系统任务 |
| `file_name` / `bucket` / `object_name` / `file_size` / `mime_type` | - | 文件元信息 |
| `status` | VARCHAR(16) | **仅** `PENDING`/`SUCCESS`/`FAILED`（中间态看 Redis） |
| `chunk_count` | INT | 成功时回填 |
| `error_msg` | VARCHAR(1024) | 失败原因（写入时自动截断 1000 字） |
| `deleted` | TINYINT | 逻辑删除（全局逻辑删配置） |
| `created_at` / `updated_at` | DATETIME | 自动填充/刷新 |

> 职责划分：**MySQL = 台账（最终状态）**；**Redis = 实时进度（中间态）**。不要往 MySQL 高频写阶段流转。

| level | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|-------|---|---|---|---|---|---|---|---|---|
| 延迟 | 1s | 5s | 10s | 30s | 1m | 2m | 3m | 4m | 5m |

## 四、设计要点提醒（少踩坑）

1. **消息体最小化**：消息里带 `taskId` + `bucket` + `objectName` 即可，进度/状态以 Redis 为准，避免消息体臃肿。
2. **生产者的发送结果必须校验**：`syncSend` 返回的 `SendResult.getSendStatus()` 非 `SEND_OK` 要按失败处理（重试或直接 `markFailed`），这是「发送可靠性」考点的落点。
3. **消费失败别吞异常**：捕获业务异常后返回 `RECONSUME_LATER`（配合消费侧重试次数），让 broker 的重试与死信机制接管；重试耗尽自动进 `%DLQ%{group}`。
4. **幂等三道防线**：`markSuccess`/`markFailed` 只允许 `PENDING→终态`（已实现）；进度写入本身可重复覆盖（Hash 天然幂等）；向量化入库步骤若可能重复，考虑按 taskId 清理旧数据或带去重标记。
5. **`%DLQ%` 的消费组单独建**：DLQ 消费失败不会再次重试（避免死循环），处理逻辑 = `markFailed` + `AlertService.alert` + 可选人工补偿。
6. **SSE 断线恢复**：推送是「尽力而为」，前端断线后应能用 `GET /api/file/task/{taskId}`（台账）+ Redis 快照恢复，SSE 只是加速手段。
7. **本地调试技巧**：`docker exec -it vllmpt-redis redis-cli -a redis123 HGETALL ai:file:task:progress:{taskId}` 直接看进度；Dashboard「消息」页可查消息轨迹、重试次数、死信 Topic。
8. **线程与背压**：200MB 文件的解析/向量化是重活，注意 `@RocketMQMessageListener` 的 `consumeThreadNumber` 与 MinIO 流式读取（别把整个文件读进内存——`getFileStream` 返回的流是流式的）。
