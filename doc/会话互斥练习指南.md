> 目标：让同一个 `sessionId` 同一时刻只允许一个推理任务在执行，避免用户连点两次「发送」时两条流并发

## 0. 这个场景要解决什么问题

### 竞态是怎么发生的

同一 `sessionId` 下，用户快速点两次「发送」，会有两个请求同时进来。走一遍代码：

| 步骤 | 代码 | 发生了什么 |
|---|---|---|
| 1 | `ChatMemoryStage` → `memoryProvider.get(sessionId)` | 两条请求**各**读到一份 `MessageWindowChatMemory`（`ChatMemoryConfig` 里每次都新建实例） |
| 2 | `ChatMemorySaveStage` → `memory.add(UserMessage...)` + `memory.add(aiMessage)` | 两条请求**各**在自己那份内存里追加了本轮问答 |
| 3 | `RedissonChatMemoryStore.updateMessages` → `list.clear(); list.addAll(json)` | 两条请求**各**做了一次「清空 + 全量覆盖写」 |

第 3 步是**非原子覆盖写**：后写的那次会把先写的整份列表覆盖掉 —— 先完成的那个请求，它的对话**凭空消失**了。

### 要保护的临界区

从「读记忆」到「写记忆」的整个区间，也就是**整条 pipeline 的执行过程**。
所以锁必须在 pipeline 入口加、在 pipeline 结束后释放。

### 为什么不能靠场景 1 的额度限制解决

场景 1 的机制是「窗口内计数 + 过期自动清理」，天然允许多个并发。
把它配成 `limit=1` 看起来像互斥，但它的兜底逻辑是**自动删除超时 member**：
一次推理跑过 `window(300s)` 之后，它的 member 会被 `ZREMRANGEBYSCORE` 清掉，
额度"凭空"释放，第二个请求就能进来了 —— **互斥被打破**。而且 ZSet 识别不出持有者，也没有续期能力。

> 一句话总结：**限流器管的是"有几个"，锁管的是"谁持有、还能持有多久"。**

## 1. 关键设计决策

| 决策点                   | 选择                                    | 理由                                                                                                   |
|-----------------------|---------------------------------------|------------------------------------------------------------------------------------------------------|
| 用 RLock 还是 SET NX PX  | **RLock**（本次只做这个）                     | 看门狗自动续期开箱即用，不用自己写续期调度                                                                                |
| `leaseTime`           | **`-1`**                              | 只有不指定租期时才启用看门狗。写成 `tryLock(0, 30, SECONDS)` 则**不会续期**，30 秒后锁自动消失                                     |
| `waitTime`            | **`0`**                               | 立即拒绝，不排队。SSE 场景下让用户盯着空屏幕等几十秒，比直接告诉他"会话处理中"更糟                                                         |
| `/stream` 加锁位置        | **`runAsync` 内部**                     | `RLock` 线程绑定，必须与解锁同线程（见第 2.2 节）                                                                      |
| `/fack` 加锁位置          | `executor.execute` 之前                 | 同步方法，加解锁天然同线程                                                                                        |
| 冲突反馈                  | `/stream` 推 `[ERROR]` 帧；`/fack` 抛 409 | 加锁在 `runAsync` 内部时响应头已发出（200 + `text/event-stream`），无法再改状态码                                          |
| 匿名会话                  | `sessionId` 为空 → 直接放行                 | 否则所有无 sessionId 的请求挤在 `ai:session:lock:null` 上互相阻塞；且 `ChatMemoryStage` 本来就会因 sessionId 缺失而 interrupt |
| 锁 key                 | `ai:session:lock:{sessionId}`         | 与场景 1 的 `ai:concurrent:{userId}` 分离，排查时一眼能分清                                                         |

## 2. 必须理解的原理

### 2.1 看门狗（Watchdog）到底做了什么

`tryLock(waitTime, leaseTime, unit)` 的 `leaseTime` 传 **-1** 时：

```
加锁成功
  ├─ Redis: HSET  ai:session:lock:{sessionId}  "<clientUuid:threadId>"  1
  ├─ Redis: PEXPIRE 该 key 30000          ← 默认租期 lockWatchdogTimeout = 30s
  └─ 启动内部定时任务（Netty 时间轮，不是 Spring 的 @Scheduled）
       每 10s（= 1/3 租期）执行一次 PEXPIRE 续期 → 30000
       ...
       └─ 直到你调用 unlock()，任务取消，key 删除
```

所以：

- **底层不是 String 而是 Hash**：`field = <clientUuid:threadId>`，`value = 重入次数`。
- 解锁时会拿当前线程的 `clientUuid:threadId` 去比对 field，对不上就拒绝 → **天然只有持有者能释放**。
- **看门狗只对"没指定 leaseTime"的加锁生效**。这是最容易踩的一点。

> 全项目已经确认没有 `@EnableScheduling` / `@Scheduled`，**不要为了这个场景引入它们**，Redisson 自己实现了续期。

### 2.2 线程绑定约束（本场景最大的坑）

`RLock` 的持有者标识包含 **`Thread.currentThread().getId()`**，所以**加锁和解锁必须在同一个线程**。

看你现在 `/stream` 的结构：

```java
// Tomcat 线程
public Flux<String> streamPipline(...) {
    ...
    CompletableFuture.runAsync(() -> {     // ← ForkJoinPool 线程，这里才是 pipeline 真正跑的地方
        executor.execute(chatPipeline, ctx);
    });
    return sink.asFlux();
}
```

- 如果**在 Tomcat 线程加锁**、在 `runAsync` 里解锁 → `isHeldByCurrentThread()` 为 `false`
  → `unlock()` 抛 `IllegalMonitorStateException`，锁永远不释放，会话被永久锁死。
- 所以 **`/stream` 的加锁必须写在 `runAsync` 内部**（和 `executor.execute` 同一个 lambda 里）。

代价：加锁失败时响应头已经发出去了，改不了状态码，只能推一帧 `[ERROR] 该会话正在处理中，请稍候再试`。
对 SSE 来说这个反馈方式是自然的 —— 前端本来就在读流。

### 2.3 两个限制的协同关系

```
请求进来
  ├─ 场景1：并发额度 tryAcquire(userId, requestId)   ← Controller 线程，失败 → HTTP 429
  └─ 场景2：会话锁  tryLockSession(sessionId)        ← /stream 在 runAsync 内，失败 → [ERROR] 帧
                                                       /fack 在 Tomcat 线程内，失败 → HTTP 409
  ↓
  finally：先 unlock 会话锁（如果拿到了），再 release 额度（一定要执行）
```

注意：**额度是在锁之前拿的**。如果锁没拿到，额度已经被占用，必须在 `finally` 里照样释放，
否则每被拒一次就泄漏一个额度。骨架里用 `boolean sessionLocked` 标志位来控制"要不要 unlock"。

## 步骤二：实现 `ChatSessionLockService`（TODO 2-1 / 2-2）

**文件**：`src/main/java/org/albedo/vllmpt/module/chat/service/ChatSessionLockService.java`

### TODO 2-1：`tryLockSession(String sessionId)`

要满足 4 条：

1. **`sessionId` 为空直接 `return true`**（放行、不加锁）。原因见设计决策表。
2. key 用 `RedisKey.sessionLock(sessionId)`，锁对象用 `redissonClient.getLock(key)`。
3. 用 `lock.tryLock(0, -1, TimeUnit.SECONDS)`：
   - `waitTime = 0` → 立刻返回，不排队
   - `leaseTime = -1` → **启用看门狗**
4. 没拿到时打 `warn`（带上 sessionId）并 `return false`。

> `tryLock` 会抛 `InterruptedException`，必须处理。正确姿势是**恢复中断标记**：
> `Thread.currentThread().interrupt();` 然后再返回 false（或者包成 RuntimeException 抛出）。
> 不要吞掉它，否则上层再也感知不到线程被中断。

骨架长这样（自己补全）：

```java
public boolean tryLockSession(String sessionId) {
    if (sessionId == null || sessionId.isBlank()) {
        return true;                       // 匿名请求不做互斥
    }
    RLock lock = redissonClient.getLock(RedisKey.sessionLock(sessionId));
    try {
        boolean locked = lock.tryLock(0, -1, TimeUnit.SECONDS);
        if (!locked) {
            log.warn("会话正在处理中，获取锁失败: sessionId={}", sessionId);
        }
        return locked;
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        log.error("获取会话锁被中断: sessionId={}", sessionId, e);
        return false;
    }
}
```

### TODO 2-2：`unlockSession(String sessionId)`

要满足 3 条：

1. **`sessionId` 为空直接 return**（和加锁时的放行策略对应）。
2. **先 `lock.isHeldByCurrentThread()` 判断，再 `lock.unlock()`**。
   不加判断会在「没持有锁 / 跨线程释放 / 重复释放」时抛 `IllegalMonitorStateException`。
3. 整个方法 `try/catch` 包住，异常只打 `error` 并**吞掉** —— 本方法总是在 `finally` 里被调用，
   抛出异常会**覆盖掉真正的业务异常**。

> 这里和场景 1 的 `release` 是同一个道理：**finally 里做的事，出错只允许记日志。**

## 步骤三：`/stream` 加锁（TODO 2-3 / 2-4）

**文件**：`module/chat/controller/ChatPiplineController.java`，`TODO [步骤2-3]` 在 `CompletableFuture.runAsync` 内部。

### 要满足的 4 条

1. **加锁写在 `runAsync` 的 lambda 里**，`executor.execute(...)` 之前（原因见 2.2 节）。
2. 拿到锁 → `sessionLocked = true`，继续跑 pipeline。
3. **没拿到锁时的动作**（顺序不能错）：

```java
sink.tryEmitNext("[ERROR] 该会话正在处理中，请稍候再试");
sink.tryEmitNext(DONE);
sink.tryEmitComplete();
return;
```

4. `boolean sessionLocked = false;` 必须声明在 `try` **外面**，这样 `finally` 才能读到。

### 为什么 `return` 放在 `try` 里是安全的

`return` 会先触发 `finally`，所以场景 1 的额度释放照样执行 —— 这正是我们要的效果
（额度已经占了，锁没拿到也必须还回去）。

### 最终结构（对照检查用）

```java
CompletableFuture.runAsync(() -> {
    boolean sessionLocked = false;
    try {
        sessionLocked = sessionLockService.tryLockSession(sessionId);   // ← TODO 2-3
        if (!sessionLocked) {
            sink.tryEmitNext("[ERROR] 该会话正在处理中，请稍候再试");
            sink.tryEmitNext(DONE);
            sink.tryEmitComplete();
            return;
        }

        executor.execute(chatPipeline, ctx);
        // ... 既有的推送逻辑
    } catch (Exception e) {
        sink.tryEmitError(e);
    } finally {
        if (sessionLocked) {
            sessionLockService.unlockSession(sessionId);                // ← TODO 2-4
        }
        concurrentLimitService.release(userId, requestId);              // 必须保留
    }
});
```

## 步骤四：`/fack` 加锁（TODO 2-5 / 2-6）

同步接口，简单很多 —— 加解锁都在 Tomcat 线程里，没有线程绑定问题。

```java
boolean sessionLocked = false;
try {
    sessionLocked = sessionLockService.tryLockSession(sessionId);       // ← TODO 2-5
    if (!sessionLocked) {
        throw new BusinessException(CODE_SESSION_BUSY, "该会话正在处理中，请稍候再试");
    }

    executor.execute(chatPipeline, ctx);
    // ... 既有逻辑

}
```

> `throw` 一定要写在 `try` 内部，否则 `finally` 不会执行，场景 1 的额度就泄漏了。

## 排错速查表

| 现象 | 最可能的原因 |
|---|---|
| 启动就报 `UnsupportedOperationException` | `tryLockSession` 还没实现 |
| 抛 `IllegalMonitorStateException` | 加锁在 Tomcat 线程、解锁在 `runAsync` 线程；必须同线程 |
| 报 `attempt to unlock lock, not locked by current thread` | 同上，或没加 `isHeldByCurrentThread()` 判断 |
| 锁 30 秒后自动消失，长推理互斥失效 | `leaseTime` 传了正数，看门狗没启用；必须传 `-1` |
| 第二个请求不报错，两个流都在跑 | 加锁写在了 `executor.execute` 之后，或者 `HGETALL` 的 key 和实际不一致 |
| 锁永远不释放，会话被锁死 | `unlockSession` 没在 `finally` 里，或 unlock 抛异常被忽略了 |
| 所有匿名请求互相阻塞 | `sessionId` 为空时没放行，锁到了 `ai:session:lock:null` 上 |
| 被拒之后并发额度不释放 | `throw`/`return` 写在了 `try` 外面，`finally` 没兜住 |
| `HGETALL` 看到的是乱码 | 这个 key 是 Redisson 自己序列化的，属正常，看 field 里是否含 `uuid:threadId` 即可 |
| 场景 1 的限流还是不触发 | 见「步骤零」：`tryAcquire`/`release` 第二个参数应该是 `requestId` 而不是 `sessionId` |

```java
public boolean tryLockSession(String sessionId) {
    if (sessionId == null || sessionId.isBlank()) {
        return true;
    }
    RLock lock = redissonClient.getLock(RedisKey.sessionLock(sessionId));
    try {
        // waitTime=0 立即返回；leaseTime=-1 启用看门狗自动续期
        boolean locked = lock.tryLock(0, -1, TimeUnit.SECONDS);
        if (!locked) {
            log.warn("会话正在处理中，获取锁失败: sessionId={}", sessionId);
        }
        return locked;
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        log.error("获取会话锁被中断: sessionId={}", sessionId, e);
        return false;
    }
}
```

### `unlockSession`

```java
public void unlockSession(String sessionId) {
    if (sessionId == null || sessionId.isBlank()) {
        return;
    }
    try {
        RLock lock = redissonClient.getLock(RedisKey.sessionLock(sessionId));
        // 必须先判断持有者，否则跨线程/重复释放会抛 IllegalMonitorStateException
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    } catch (Exception e) {
        // 本方法总在 finally 中调用，这里抛出会覆盖真正的业务异常
        log.error("释放会话锁失败: sessionId={}", sessionId, e);
    }
}
```

## 加餐：如果不用 Redisson，手写版怎么做

`doc/todo.txt` 里的第二个考点。思路：

```text
加锁：SET ai:session:lock:{sessionId} {requestId} NX PX 30000
      → 成功（返回 OK）= 拿到锁；失败 = 已被占用

续期（看门狗）：后台定时任务，每 10s 执行 Lua：
      if redis.call('GET', KEYS[1]) == ARGV[1] then
          return redis.call('PEXPIRE', KEYS[1], ARGV[2])
      else
          return 0
      end
      → 注意必须用 Lua 做 CAS，否则会把别人的锁续上

释放：同样的 Lua CAS，value 相等才 DEL
      → 这一步是"只能持有者释放"的关键，直接 DEL 会把别人的锁删掉
```

和 RLock 版的差异：

| | Redisson RLock | 手写 SET NX PX |
|---|---|---|
| 持有者标识 | `clientUuid:threadId`（Hash field） | 你自己传的 `requestId` |
| 续期 | 看门狗，开箱即用 | 自己写定时任务 |
| 可重入 | 支持（Hash value 计数） | 需要自己实现计数 |
| 是否线程绑定 | **是** | **否**（所以可以跨线程加解锁） |
| 代码量 | 3 行 | ~50 行 + 一个调度器 |

手写版最大的好处是**不线程绑定**，可以在 Tomcat 线程加锁、在 `runAsync` 线程解锁 —— 
那样 `/stream` 就能在返回 Flux 之前拿到锁，冲突时直接返回 409（和 `/fack` 一致）。
如果以后想统一两个接口的冲突反馈，这就是改造方向。
