## 一、任务目标

### 1.1 业务背景

当前 RAG 链路只用 Chroma 做向量检索，对**精确关键词**（产品型号 `X-990A`、特定人名、版本号）效果很差：
embedding 会把字面信息“语义化”，型号/编号这类 token 在语义空间里没有稳定含义，容易被“语义相近但字面无关”的噪音淹没。

混合检索 = **BM25 字面匹配**（补精确词的短板）+ **向量语义召回**（补近义表达的短板），两路互补。

### 1.2 核心需求（来自 todo.txt）

1. **双写双索引**：文档分块后，同时写入 Chroma（向量）和 ES（倒排索引）。
2. **双路检索**：查询时，同时发起向量检索和 ES 的 BM25 全文检索。
3. **RRF 融合**：用 RRF (Reciprocal Rank Fusion) 算法融合两路结果，返回 Top-K。

### 1.3 技术考点（ES 版）

| 考点 | 对应机制 | 提示 |
|------|---------|------|
| ES DSL 语法（必修） | `multi_match` / `bool` / `function_score` | 先在 Kibana Dev Tools 验证 DSL，再翻译成 fluent Java API |
| BM25 算分原理 | 词频饱和 + 文档长度归一化 | 命中词越多分越高，但边际递减；长文档不会靠“堆词”挂分 |
| Function Score Query | 在 BM25 分基础上叠加业务因子 | 进阶：`createdAt` 越新得分越高（时间衰减），或 fileName 精确命中加权 |
| Multi-search API | `msearch`：一次 HTTP 发多个搜索请求 | 进阶：把 BM25 路拆成“content 全文 + fileName 精确”两个查询用 msearch 合并；本项目两路异构（Chroma + ES），融合发生在应用层 |
| RRF 融合 | `score = Σ 1/(k+rank)`，k=60 经典值 | 只用**名次**不用原始分数，天然规避 BM25 分与余弦相似度的量纲差异 |

### 1.4 完成标准（自检清单）

- [ ] 放入一份文本文件入库后，**Chroma 和 ES 里都有同一份分块**（双写生效）
- [ ] Kibana 中 `GET vllmpt_knowledge_chunks/_count` 与分块数一致；`content` 字段是 IK 分词（写 `ik_max_word` / 查 `ik_smart`）
- [ ] 实现 `HybridSearchService.bm25Search`（TODO 1）：DSL 查询按相关度降序返回文本列表
- [ ] 实现 `HybridSearchService.rrfFuse`（TODO 2）：RRF 融合两路结果
- [ ] `POST /api/hybrid/search` 返回融合后的 Top-K；**专有名词查询命中优于纯向量检索**
- [ ] 幂等：同一 `taskId + chunkIndex` 重复写入 ES 不产生重复文档（文档 id 自动覆盖）
- [ ] 设计问答：能解释为什么 RRF 不需要对两路分数做归一化

## 三、接口文档

### 3.1 HTTP 接口

统一返回结构：`Result<T>` = `{ "code": 200, "message": "Success", "data": ... }`

#### 【已就绪 · 待 TODO 补全】混合检索（场景4 主入口）

```
POST /api/hybrid/search?topK=5
Body: 查询词（raw text，非 JSON 对象）     // 如：X-990A 支持哪些功能
Resp: { "code":200, "data": ["分块文本1", "分块文本2", ...] }   // RRF 降序
```

内部流程：BM25 检索（ES，取 `topK*2`） + 向量检索（Chroma，取 `topK*2`） → RRF 融合 → Top-K。

#### 【参考】现有向量检索/入库接口（chat 模块旧链路，未动）

```
POST /api/indexAction/searchEmbd      // body: 查询词；只走向量路（不融合），用于对比
POST /api/indexAction/indexString     // body: 单段文本；直接向量化入库
```

### 3.3 ES 索引结构：`vllmpt_knowledge_chunks`

启动时由 `KnowledgeChunkIndexInitializer` 自动创建（存在则跳过）。

| 字段 | 类型 | 分词 | 说明 |
|------|------|------|------|
| `content` | text | 写 `ik_max_word` / 查 `ik_smart` | 分块正文，BM25 检索主体 |
| `fileName` | keyword | - | 精确匹配/聚合用 |
| `taskId` | keyword | - | 归属任务（场景6 关联键） |
| `chunkIndex` | integer | - | 块序号 |
| `source` | keyword | - | 来源标记 |
| `createdAt` | date (epoch_millis) | - | 写入时间，function_score 时间衰减可用 |

**文档 id 约定**：`taskId:chunkIndex`（`EsChunkIndexer` 自动生成）——重复写入覆盖同一文档，天然幂等；缺 taskId 时由 ES 自动生成 id。

## 四、设计要点提醒（少踩坑）

1. **双写接线（需求1 落点）**：`DualIndexWriter` 目前无人调用，两个接法——
   - **方案 A（推荐）**：场景6 补全 `EmbedConsumer` 时，把分块入库调用从
     `knowledgeBaseRagService.indexTextSegment(segment)` 换成 `dualIndexWriter.indexSegment(segment)`
     （或整批 `indexSegments(segments)`）。记得给 metadata 打上 `taskId`（ES 幂等 id 依赖它）。
   - **方案 B**：改造 `TextEmbedding.chunkEmbeding`（影响旧同步链路，不推荐）。
2. **双写一致性**：策略是“先 Chroma 后 ES，任一失败直接抛异常”，由上层重试机制兜底
   （场景6 的 MQ 重试 / 旧链路自行补偿）。重试时 ES 侧靠幂等 id 免疫重复；**Chroma 侧 add 可能产生冗余向量**，
   生产上可考虑按 taskId 先删后写或定时对账。
3. **版本对齐不要动**：client 8.11.4 / server 8.11.0 必须同 minor（跨大版本会被服务端拒绝）；
   `pom.xml` 里 `dependencyManagement` 钉死 `elasticsearch-rest-client` 8.11.4 是为了防 Spring Boot BOM 把它顶到 9.x——不要删。
4. **IK 两个分词器的分工**：写入用 `ik_max_word`（细粒度，多切多召回），查询用 `ik_smart`（粗粒度，少噪音）。
   这也是 mapping 里 `analyzer` / `search_analyzer` 分开配的原因。
5. **RRF 只看名次**：`1/(60+rank)` 里 rank 从 1 开始；两路都进 Top 的 chunk 拿两次分会被顶到最前。
   k=60 是经典值，不需要调参——先写对公式，再谈优化。
6. **候选池放大**：每路取 `topK*2` 再融合，给“双路都靠前”的文档更多叠加机会；纯单路霸榜的也有票。
7. **BM25 路的降级**：ES 挂了返回空列表由向量路兜底（骨架注释里已给 try/catch 模式），
   混合检索的高可用就是“允许一路失败”。
8. **调试顺序**：Kibana Dev Tools 跑通 DSL → 翻译成 Java 补 TODO 1 → 补 TODO 2 → 调 `/api/hybrid/search`
   用专有名词查询，和 `/api/indexAction/searchEmbd`（纯向量）对比命中效果。
