场景一：
新场景名：基于 ZSet 的“单用户并发推理任务数”限制（Concurrency Control for LLM Inference）
业务背景：大模型推理（尤其是 72B 级别）极其消耗 GPU 算力。如果不对单用户的并发请求数做限制，恶意用户或写错代码的客户端可能会同时发起 100 个 SSE 流式对话，瞬间打满 GPU 显存或导致队列严重拥堵，影响其他正常用户。
核心需求：限制同一个 userId 同一时间最多只能有 N 个（如 3 个） 正在进行的推理任务。
为什么比 Token 扣减好？

场景 2：SSE 流式会话的并发互斥与“看门狗”机制
业务背景：同一个 sessionId 下，如果用户快速连续点击两次“发送”，会导致两个 SSE 流同时修改 Redis 中的记忆上下文，造成上下文错乱。


场景 3：基于 Redis 的"每日 Token 配额"原子扣减与用量统计
1. 业务背景
大模型推理是按 Token 计费的（输入 Token + 输出 Token）。你的平台给每个用户设定了每日免费额度（比如每天 10000 Token）。
用户每次对话，AI 返回后，你需要立刻扣减对应的 Token 数。
如果用户今天已经用完了 10000 Token，下一次请求应该直接拒绝，提示"今日额度已用完，请明天再来"。
每天凌晨 0 点，额度自动重置。



旧的场景 3：基于 Redis Pub/Sub 的“主动取消”指令广播与推理任务秒级回收
1. 业务背景（为什么场景1和2还不够？）
在场景1和2中，我们完美解决了“防超发”和“防并发冲突”的问题。但是，大模型推理（LLM Inference）有一个致命特点：耗时极长（通常 10秒 ~ 3分钟）。
灾难场景推演：
用户发起了一个推理请求，系统分配了 GPU 资源，开始流式输出（SSE）。此时，场景1的 ZSet 记录了一条并发额度。
输出到一半，用户觉得回答方向不对，点击了“停止生成”按钮；或者用户的网络突然断开，SSE 连接中断。
痛点爆发：
GPU 算力浪费：后端的 Java 推理线程如果感知不到客户端断开，会继续向大模型 API 发送请求，白白消耗昂贵的 GPU 算力。
额度“幽灵”占用：虽然 SSE 断了，但场景1中 ZSet 里的并发额度并没有立刻释放（只能等 windowMs 窗口滑动，或者等看门狗超时）。在这几十秒内，用户想发新问题，系统会提示“并发请求过多”，用户体验极差。
2. 核心需求
实现一个跨节点的、秒级的任务取消与资源回收机制：
当用户点击“停止”或 SSE 断连时，立刻向 Redis 发送一条“取消指令”。
正在执行推理的 Java 线程（可能部署在集群的另一台机器上）能立刻收到该指令。
推理线程收到指令后，立刻中断当前的 LLM 推理流（调用大模型 API 的 cancel 方法）。
中断后，立刻级联释放场景1的并发额度（ZREM）和清理相关状态，让 GPU 和 Redis 资源瞬间回血。
3. 技术考点（深度挖掘）
这个场景将考察你对 Redis 消息机制和 Java 并发控制的深度结合：
Redis Pub/Sub (发布/订阅机制)：
使用 PUBLISH 发送取消指令（Payload 包含 requestId）。
使用 SUBSCRIBE 监听取消频道。
进阶考点：Redisson 的 RTopic 封装，或者处理 Pub/Sub 连接断开时的重连机制。
SSE 断连的精准感知：
利用 Spring SseEmitter 的 onCompletion, onTimeout, onError 回调，精准捕获客户端断开事件，作为触发 Pub/Sub 发布的源头。
Java 线程的优雅中断 (Graceful Interruption)：
如何在深层嵌套的推理代码中停止？不能简单粗暴地 Thread.stop()。
需要结合 volatile boolean cancelled 标志位，或者在阻塞 IO（如等待大模型返回 token）时调用 Thread.interrupt() 并捕获 InterruptedException。
资源的级联清理 (Cascade Cleanup)：
在推理线程的 finally 块中，确保调用 concurrentLimitService.release() 和清理上下文，保证状态机闭环。

设计文档见：doc/场景3.md
（文档里定义了两种中断意图：USER_STOP 走硬中断立刻释放；CLIENT_DISCONNECT 走静默模式，
  停止推流但继续生成，生成完再释放。两者都只打标记，资源释放统一由工作线程的 finally 完成。）

二、 Elasticsearch 进阶场景：从“日志存储”到“复杂检索与多维分析”
文档中 ES 目前主要用于日志存储。我们需要将其引入核心业务链路。
场景 4：RAG 知识库的“混合检索” (Hybrid Search)
业务背景：文档 4.3 中目前只用 Chroma 做向量检索。但向量检索对“精确关键词”（如产品型号 X-990A、特定人名）效果很差。
核心需求：
将文档分块后，同时写入 Chroma (向量) 和 ES (倒排索引)。
查询时，同时发起向量检索和 ES 的 BM25 全文检索。
使用 RRF (Reciprocal Rank Fusion) 算法融合两路结果的得分，返回 Top-K。
技术考点：
ES 的 Function Score Query 和 BM25 算分原理。
ES 的 Multi-search API 批量并发查询。
Python 迁移映射：LlamaIndex 和 LangChain 都有现成的 HybridRetriever，但理解 ES 的 DSL (Domain Specific Language) 查询语法是必修课。
场景 5：全链路对话日志的多维聚合与下钻分析
业务背景：老板要看报表：上个月各模型的 Token 消耗总额、RAG 召回的平均耗时、各业务线（BizScene）的错误率。
核心需求：
设计 ES 的 Index Mapping（区分 keyword, text, date, nested 类型）。
编写复杂的 DSL 聚合查询：按“业务线”分组 -> 按“模型”子分组 -> 计算 Token 总和与 P99 耗时。
技术考点：
Aggregations (聚合分析)：Terms Agg, Date Histogram, Metrics (Sum, Avg, Percentiles)。
Pipeline Aggregations：在聚合结果之上再做二次计算（如计算移动平均）。
Python 迁移映射：Python 中使用 elasticsearch-dsl 库可以像写 ORM 一样写 ES 查询，极大提升开发体验。



三、 消息队列 (kafka) 进阶场景：从“简单异步”到“复杂状态机与可靠性”
文档 10.3 规划了 MQ 用于文件解析。我们需要设计更健壮的架构。
场景 6：百 MB 大文件 RAG 入库的“异步流水线与进度追踪”
业务背景：用户上传 200MB 的 PDF，后端如果同步处理会超时。必须异步化，且前端需要看到“解析中(30%) -> 分块中(60%) -> 向量化中(90%) -> 完成”的进度。
核心需求：
设计 MQ 拓扑：file.parse.exchange (Direct) -> parse.queue -> embed.queue。
消费者处理完一个阶段，将进度写入 Redis，并通过 WebSocket/SSE 推送给前端。
如果向量化阶段失败（如 Chroma 宕机），消息进入死信队列 (DLQ)，并触发告警。
技术考点：
RabbitMQ 路由机制：Direct / Topic 交换机的使用。
消息可靠性：Publisher Confirm, 消费者 Manual ACK, 死信队列 (DLX) 配置。
延迟队列：使用 rabbitmq_delayed_message_exchange 插件处理超时未响应的任务。
Python 迁移映射：Python 中通常不直接写底层 AMQP 协议，而是使用 Celery (结合 Redis/RabbitMQ 作为 Broker) 或 aio-pika (异步原生客户端)。学习 Celery 的 Canvas (Chain, Chord, Group) 非常适合这个场景。
场景 7：Agent 工具调用的异步 RPC 模式
业务背景：ReAct 循环中，模型决定调用“生成月度报表”工具。这个工具需要查库、画图，耗时 1 分钟。不能阻塞主线程。
核心需求：
Agent 发起工具调用请求，放入 MQ，立即返回“处理中”。
后台 Worker 执行完毕后，将结果放入 reply.queue。
Agent 监听 reply.queue，收到结果后继续下一轮推理。
技术考点：
RPC 模式 (Reply Queue)：RabbitMQ 实现同步转异步的经典模式。
Correlation ID：确保请求和响应正确匹配。


四、 复杂 SQL 查询进阶场景：突破 CRUD，掌握关系型数据的高级玩法
AI 项目虽然重 NoSQL，但用户、权限、账单、对话树等核心业务依然依赖 MySQL。
场景 8：对话树 (DAG) 的存储与递归查询
业务背景：文档附录 P1 提到的“对话树分支管理”。用户修改了第 3 轮对话，重新生成了第 4 轮。此时对话不再是线性链表，而是树形结构（DAG）。
核心需求：
设计表结构：chat_message(id, session_id, parent_id, content, model, created_at)。
查询某条消息的所有祖先节点（用于组装当前上下文）。
查询某个 Session 下的所有叶子节点（用于展示对话分支）。
技术考点：
递归查询 (Recursive CTE)：使用 WITH RECURSIVE 语法实现树形数据的向上/向下遍历。
闭包表 (Closure Table) 或 路径枚举 设计模式对比。
Python 迁移映射：Python 的 SQLAlchemy 2.0 对 CTE 和递归查询有非常好的原生支持。
场景 9：多维度 Token 消耗账单与阶梯计费报表
业务背景：财务需要出账单。不同模型单价不同，且用户有“每月前 10 万 Token 免费，超出部分 0.01元/千 Token”的阶梯计费规则。
核心需求：
按“用户 + 月份”分组，统计各模型的 Token 消耗量。
计算每个用户的总费用（需处理阶梯计费逻辑）。
生成排行榜（Top 10 消耗用户）。
技术考点：
窗口函数 (Window Functions)：SUM() OVER(PARTITION BY ...)，ROW_NUMBER()。
高级分组：GROUP BY ... WITH ROLLUP (生成小计和总计行)。
复杂 CASE WHEN 结合子查询实现阶梯计费逻辑。
Python 迁移映射：虽然 Python 有 Pandas 做数据分析，但在高并发 Web 后端，掌握 SQLAlchemy 的复杂 SQL 构建或手写原生 SQL 依然是高级后端的标志。



补充:
一个典型的通义千问（Qwen）网页端或客户端向后端发送的对话请求参数（Request Payload）
这些字段位于最外层，用于控制整个请求的会话状态和通信方式。
chat_id: 字符串 (UUID)。当前对话窗口的唯一标识符。用于区分用户创建的不同聊天会话。
model: 字符串。指定本次对话使用的大模型版本。这里是 "qwen3.7-plus"（注：目前官方公开多为 qwen-plus/max 等，这可能是内部测试版本号或笔误）。
chat_mode: 字符串。对话模式。"normal" 表示普通对话模式，可能还有 agent（智能体）、search（搜索）等模式。
stream: 布尔值。是否开启流式输出。true 表示开启，即“打字机”效果，模型生成一个字就返回一个字，而不是等全部生成完再返回。
incremental_output: 布尔值。配合 stream: true 使用。true 表示增量返回（每次只返回新生成的文本），false 表示全量返回（每次返回从开头到当前的完整文本）。
version: 字符串。API 或通信协议的版本号，这里是 "2.1"。
parent_id: 字符串 (UUID)。顶层请求的父消息 ID。在多轮对话中，用于告诉后端当前请求是基于哪一条历史消息发起的。
timestamp: 数字。请求发起时的时间戳（秒级或毫秒级）。
二、 消息内容与结构参数 (messages 数组)
这个数组包含了当前发送的具体消息内容。现代大模型前端通常采用对话树（DAG） 结构，而不仅仅是线性的列表，因此包含了很多用于维护树结构的字段。
content: 字符串。用户实际发送的文本内容，这里是 "你可以做到什么"。
role: 字符串。消息发送者的角色。这里是 "user"（用户），还可能是 "assistant"（AI）或 "system"（系统）。
fid / id: 字符串 (UUID)。当前这条消息节点的唯一标识符（Feature ID / Forward ID）。
parentId / parent_id: 字符串 (UUID)。当前消息的父消息 ID。用于将当前消息连接到上一条消息，形成对话链条。（注：代码中同时出现了驼峰和下划线命名，可能是前端序列化时的兼容处理）。
childrenIds: 数组。当前消息的子消息 ID 列表。这是支持“对话分支”的关键。例如：你对 AI 的同一个回答不满意，点击了“重新生成”，或者你修改了历史问题，就会产生新的分支，这些分支的 ID 都会记录在父消息的 childrenIds 中。
chat_type / sub_chat_type: 字符串。聊天类型。"t2t" 代表 Text-to-Text（文本到文本），用于区分文生图、文生视频等其他模态的对话。
files: 数组。用户上传的附件（如图片、PDF文档等），这里为空 [] 表示纯文本对话。
models: 数组。该消息指定使用的模型列表。有时用于多模型对比或特定的路由分发。
user_action: 字符串。用户的动作类型。"chat" 表示正常发送消息，可能还有 "retry"（重新生成）、"edit"（编辑历史消息）等。
timestamp: 数字。该条消息创建/发送的时间戳。
三、 扩展元数据 (extra)
用于传递一些非核心的、扩展的上下文信息。
extra.meta.subChatType: 进一步细化聊天类型，这里也是 "t2t"，与外层的 sub_chat_type 呼应。
四、 高级特性控制 (feature_config)
这是控制大模型高级能力（如深度思考、联网搜索）的核心配置。
thinking_enabled: 布尔值。是否开启 “思考/推理”模式（类似 QwQ 或 DeepSeek-R1）。开启后，模型会在回答前展示内部的思考过程（CoT）。
auto_thinking: 布尔值。是否自动触发思考模式。如果为 true，模型会根据问题的复杂度自动判断是否需要进入深度思考。
output_schema: 字符串。控制输出的结构或阶段。"phase" 可能意味着分阶段输出（例如：先输出思考阶段，再输出最终回答阶段）。
research_mode: 字符串。研究/联网搜索模式。"normal" 表示普通模式，可能还有 "deep"（深度搜索/研究）等，用于控制模型是否调用搜索引擎以及搜索的深度。
